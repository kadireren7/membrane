# MEMBRANE v0.4 roadmap

**Planning document (Phase 32). No runtime behavior changed to produce
this document.** See `docs/product-direction.md` for the underlying
product thesis/persona/positioning this roadmap is built on.

## Decision record

- **PRIMARY V0.4 THEME:** From configuration to recommendation —
  closing the last major "you must already know a memory-relevant
  number yourself" gap (`--ctx`).
- **PRIMARY FEATURE:** Safe context recommendation / auto-sizing (§3).
- **SECONDARY FEATURES:** model-family compatibility expansion (max 2
  targets, §6), opportunistic hardware-validation broadening (§7),
  upstream-hook feasibility investigation only, no PR (§9).
- **NON-GOALS:** see §10.
- **SUCCESS CRITERIA:** see §11.
- **PHASE ORDER:** see §13.
- **RISKS:** see §14.
- **DEFERRED ITEMS:** CUDA (no validation hardware, §8), config file
  (§8), APT repository (§8, → v0.5), signed/reproducible releases
  (§8, → v0.5), performance work (§8, unless new evidence appears),
  issue-bundle export (nice-to-have, not a dedicated phase).

## 1. Current user friction (validated against the actual repo, not
invented)

Every item below was checked against the live CLI/docs before being
listed — none of these are already solved:

- `--auto` still requires an explicit `--ctx` (`tools/membrane-run/
  product_cli.cpp`'s own validation: `--gpu-layers all|auto|N`, which
  `--auto`'s own implicit fill-in resolves to, unconditionally requires
  `--ctx` unless the request is `--plan-only` with `--ctx` already
  given — confirmed directly, Phase 30's own narrow fix).
- No way to ask MEMBRANE for a *recommended* context — no such flag or
  mode exists anywhere in `product_cli.cpp`.
- `--inspect-model` (Phase 30) reports architecture/compatibility and,
  if `--ctx` is supplied, a KV-byte estimate *at that context* — but it
  never reads host RAM or GPU VRAM, and never recommends a context
  itself. It answers "is this compatible," not "what should I use."
- The user must manually decide whether to try 2048, 4096, 8192, etc. —
  no bounded, ranked alternative set is ever shown.
- `--plan-only` shows the *one* resolved plan for the `--ctx` the user
  already chose, never alternatives at other context sizes.
- Compressed-KV model-family support is still narrow (`llama` +
  `qwen2` only, and `qwen2` scoped to one specific fixture).
- Packaging is Debian-family amd64 only (`results/release-artifacts/
  manifest.json`).
- No config file or persistent user preferences exist anywhere in the
  codebase (confirmed: no config-parsing code, no documented config
  path).

## 3. Why context recommendation is the primary feature

MEMBRANE already solves GPU layers, KV precision, and KV placement
automatically via `--auto`. The one remaining flag every user must
still supply themselves, with no help from the product, is `--ctx` —
and it's arguably the most consequential one (it drives KV memory
directly). Closing this gap is what makes the aspirational thesis in
`docs/product-direction.md` §3 actually true. No other candidate in
the table above scores as high on user value while reusing this much
existing infrastructure.

## 4. Context-recommendation feasibility (source-level only — nothing
implemented this phase)

**Available pre-model-load today** (verified against the real source):

- Real host RAM, total + available: `read_host_meminfo()`
  (`tools/membrane-run/main.cpp`, `/proc/meminfo`) — cheap, already
  used by `--doctor`.
- Real per-device GPU free/total VRAM: `membrane_gpu_list_devices()`
  (`tools/membrane-run/gpu_device.cpp`) — cheap, real driver query,
  already used by `--list-devices`/`--doctor`.
- Model weight-byte estimate (total, per-layer, output-role) and the
  hparams needed for KV math (`n_embd`, `n_head`, `n_head_kv`,
  `n_layer`, `arch_name`): `membrane_gpu_estimate_model()`
  (`gpu_device.cpp`) — a pure GGUF metadata scan
  (`gguf_init_from_file`, `no_alloc=true`), no tensor data loaded, no
  model load. Already used by `--inspect-model`/`--doctor`.
- KV bytes per precision mode at a *given* context:
  `kv_bytes_for_mode()` (`main.cpp`) — deterministic, real `ggml`
  block-format math, already used everywhere.
- The existing safety-reserve formula (`gpu_policy.h`: the larger of
  15% of device total or a 512 MiB fixed floor) — already used by
  `--gpu-layers auto`.
- The existing joint planner (`joint_planner.h`,
  `membrane_joint_plan_resolve()`) — resolves one legal
  (gpu_layers, kv_precision, kv_placement) combination for one *given*
  `ctx_size`, already ranking candidates internally.

**NOT available pre-model-load today — real gaps:**

- **The model's own trained/supported maximum context**
  (`{arch}.context_length` in GGUF, i.e. `n_ctx_train`) is **not
  currently read anywhere in this codebase.** `membrane_gpu_estimate_
  model()`'s `hparams_available` struct has no such field. This is a
  small, well-precedented addition (same pattern already used for
  `n_embd`/`n_head`/etc. — an arch-prefixed GGUF key read in
  `gpu_device.cpp`'s existing `read_hparams()`), not a redesign.
- **Real `ggml` compute-buffer memory at context-creation time** — the
  transient graph-allocation overhead beyond the KV cache itself — is
  **not modeled anywhere in this project today.** `kv_bytes_for_mode()`
  covers KV cache only; the weight-byte estimate covers weights only.
  This is a genuine, disclosed unknown: the existing safety reserve
  partially absorbs it but was never derived *from* a real
  compute-buffer measurement. A context recommendation must not claim
  a guarantee this project cannot back — see Risk R1.
- **Real prompt token count** is only known for one specific run, not
  for a general "recommend me a context" query independent of any
  prompt. A first version should default to a reasonable headroom
  assumption rather than assume zero prompt tokens; supplying a
  representative prompt as an optional recommendation input is a
  plausible future refinement, out of scope for the first slice.

**Classification:**

| | |
|---|---|
| HARD CONSTRAINT | Model's own max context (once read); `compat_check.c`'s architecture allowlist |
| DYNAMIC MEASUREMENT (point-in-time, can change before a real run) | Host available RAM; GPU free VRAM |
| ESTIMATE (real formula, not a live measurement) | KV bytes per mode/context; weight bytes |
| UNKNOWN (not modeled today) | Real `ggml` compute-buffer overhead at context-creation time |

## 5. `MODEL_MAX_CONTEXT` vs. `HARDWARE_FIT_CONTEXT` vs.
`RECOMMENDED_CONTEXT`

These are three genuinely different numbers and must stay three
separate, clearly-labeled fields in any future output — never
conflated:

- **`MODEL_MAX_CONTEXT`** — the model's own trained/supported maximum
  (the GGUF's `{arch}.context_length`). A property of the *model*,
  independent of hardware.
- **`HARDWARE_FIT_CONTEXT`** — the largest context that fits within
  *this machine's* real, currently-available memory for a given KV
  precision/placement combination. A property of *this host, right
  now* — computed by walking a bounded candidate set through the
  existing joint planner (§6) and the existing safety reserve.
- **`RECOMMENDED_CONTEXT`** — MEMBRANE's actual suggestion: the largest
  `HARDWARE_FIT_CONTEXT` that does not exceed `MODEL_MAX_CONTEXT`,
  snapped to a bounded candidate value (never the raw theoretical
  maximum, to preserve headroom against §4's unmodeled compute-buffer
  risk). Always `RECOMMENDED_CONTEXT <= min(MODEL_MAX_CONTEXT,
  HARDWARE_FIT_CONTEXT)`.

A model reporting a max of 32768 on a machine that can only safely fit
4096 must show both numbers, never just one — hiding either would be
actively misleading.

## 6. Recommendation-engine boundary: reuse, never a second planner

The recommendation "engine" is explicitly **not** a new decision
algorithm. It is: for each candidate context in a small, fixed,
deterministic list (smallest to largest), call the *existing*
`membrane_joint_plan_resolve()` (or the CPU-only adaptive-KV path for
a non-GPU host) with that context, keep it if it resolves to a legal
plan, and pick the largest legal candidate that does not exceed the
model's own max context. Zero new ranking/scoring logic — *which*
`(gpu_layers, kv_precision, kv_placement)` combination wins for a
*given* context remains 100% the existing joint planner's job,
untouched. This directly satisfies the task's own instruction ("prefer
reuse; do not create a second planner") and is Risk R4's primary
mitigation.

**Candidate set:** a small doubling sequence (e.g. 512 → 32768, ~7
steps) plus the model's own max context always appended as an explicit
final candidate (a model may report an unusual non-power-of-two max, and
§5 requires it stay independently inspectable). Each joint-planner
resolve is already measured as cheap (Phase 24/25: planner time is a
tiny fraction of total run time), so 7-8 resolves is negligible cost.
**Exact boundary values are an implementation-phase decision, not
locked in by this planning document** — the shape (small, bounded,
deterministic, doubling) is what matters here.

**Hard constraint (§14 of the Phase 32 task):** no brute-force scan
over every context size, no performance benchmarking inside the
recommendation, no real allocation/probing — memory estimates only,
the same arithmetic the planner already uses.

## 7. UX design

### 7.1 Ranked options

The task lists five candidate UX shapes. Ranked, with the stated
preference ("recommendation before silent automatic behavior unless
safety proof is strong") taken seriously given §4's real, disclosed
unmodeled-risk gap:

1. **`--ctx auto`** (opt-in, never the default — same naming
   convention as `--gpu-layers auto`/`--kv adaptive`/`--kv-placement
   auto`, all already established, opt-in-only patterns in this CLI).
   Always reports what it selected and why in both human and JSON
   output (same transparency convention `adaptive` KV already has).
   Compatible with `--plan-only` (matches the exact pattern Phase 30
   already established for `--plan-only` + no `--prompt`). **This is
   not "Option A" as literally described in the task** (a silent
   `--auto`-implied default) — it is Option C, explicit and always
   self-reporting, which is what actually satisfies "never silent."
2. **Extend `--inspect-model`** (already exists, already read-only, no
   generation) to show a recommendation + a bounded alternatives list
   whenever host/GPU info is available — the "look before you leap"
   path (closest to the task's Option B), companion to #1, not a
   replacement.
3. Rejected as primary: a bare `--auto` that silently invents a
   context with zero opt-in signal (the task's literal Option A) —
   contradicts this project's own established "never invent a memory
   number silently" principle (the exact rule `--inspect-model`'s own
   `--ctx` handling was built around in Phase 30).
4. Rejected: `--ctx max-safe` (Option D) — an unnecessary second
   spelling of the same "auto" concept this CLI already has a
   consistent naming pattern for; risks becoming exactly the kind of
   marketing-preset creep Phase 28 explicitly avoided (`--safe`,
   `--fast`, etc. were deliberately never added).
5. Rejected as the *sole* option: recommend-only, never auto-run
   (Option E) — too much friction for the common case and undercuts
   the v0.4 thesis of one-command convenience; effectively already
   covered as a strict subset of #1 + #2 together (a user who wants
   recommend-only just uses `--inspect-model` and never types `--ctx
   auto`).

**Chosen design:** `--ctx auto` for the run path (opt-in, always
self-reporting, `--plan-only`-compatible) plus an extended
`--inspect-model` for the look-before-you-leap path. Reuses two
already-existing, already-understood CLI surfaces rather than
inventing a third top-level flag — directly mitigates Risk R8 (CLI
complexity growth).

## 8. Deferred and decided-against items

- **CUDA — `DEFERRED_NO_VALIDATION_HARDWARE`.** `llama.cpp`/`ggml`
  already has a mature, first-party CUDA backend; MEMBRANE's own
  device-enumeration code (`gpu_device.cpp`) is written against the
  vendor-neutral `ggml_backend_dev_t` abstraction (proven working
  identically across AMD RADV and NVIDIA Vulkan today, no
  backend-specific branching found in MEMBRANE's own code) — a
  genuinely encouraging technical signal that CUDA offload might work
  with little or no MEMBRANE-side change once `-DGGML_CUDA=ON` is
  used to build `llama.cpp`'s own CMake. But it cannot be locally
  validated today: no confirmed CUDA driver/toolchain installation on
  the maintainer's host, even though the existing NVIDIA GTX 1650 is
  CUDA-capable hardware in principle. Installing a CUDA toolkit to
  check this cheaply is a plausible, low-cost *investigation* note for
  a future phase — **not a v0.4 roadmap commitment**, and not
  implemented without real validation hardware, per this project's own
  evidence-based culture.
- **Config file — DEFER, not v0.4.** Once §7's context recommendation
  ships, the common-path CLI is already short
  (`--model X --prompt "..." --ctx auto`). A config file's main value
  (not retyping flags) is comparatively marginal against its real cost
  (new state, CLI-vs-config precedence rules, a new support-burden
  surface: "why isn't my config being picked up"). Not added merely
  because mature tools have one.
- **APT repository — DEFER to v0.5.** High UX value, but real,
  ongoing operational cost (signing infrastructure, repo hosting,
  metadata maintenance, release automation, ongoing security
  responsibility) for a currently single-maintainer project
  (`SUPPORT.md`: "single-maintainer research project, no formal SLA").
  Signed releases (below) are a natural prerequisite — you don't want
  users trusting an unsigned third-party apt source — so this
  naturally follows that work, not precedes it.
- **Signed releases / supply chain — v0.5 maturity work, not v0.4.**
  Recorded honestly: the `v0.3.0` tag is annotated but **unsigned** —
  no GPG/SSH tag signing was set up. Future v0.5 candidates: signed git
  tags, a signed `SHA256SUMS`/package, an SBOM for the `.deb`, build
  provenance, reproducible builds. All real, all deferred — more
  valuable once there's an actual growing external install base to
  protect, which v0.4's own feature work (not distribution polish) is
  what should grow first.
- **Performance work — SECONDARY / DEFERRED unless new evidence
  appears.** Phase 24/25's own evidence-backed conclusion stands: no
  safe MEMBRANE-owned optimization was found (model load and decode
  are both fully third-party cost). Re-litigating this without new
  profiling evidence would be scope creep, not product work.
- **Diagnostics/issue-bundle export (F9) — nice-to-have, not a
  dedicated phase.** Real value (helps a future external bug report be
  useful, especially given limited independent validation), low
  complexity (mostly aggregating already-existing `--doctor`-class
  output), but not core to the v0.4 thesis. Candidate for the
  hardening phase (§13, Phase 39) if time allows, not its own phase.

## 9. Model-family expansion (max 2 targets)

Selection criteria, matching the exact rigor `Qwen2.5-1.5B-Instruct`
was vetted against in Phase 26 (source-level proof that an
architecture falls through the same generic, non-hybrid, non-SWA KV
cache construction path `llama-model.cpp`'s `create_memory()` uses —
never popularity alone):

- **Mistral — top candidate.** Well-known architectural closeness to
  `LLM_ARCH_LLAMA` in `llama.cpp` (RMSNorm, RoPE, GQA, SwiGLU — the
  same shape class the existing allowlist already covers), high user
  relevance. **Not yet source-verified** the way Qwen2 was — that
  verification is the *first* real task of whichever phase picks this
  up (Phase 36, §13), not something asserted as already true here. No
  local fixture exists today; acquiring one is a real, one-time,
  flagged dependency (no download happens in this planning phase).
- **Phi-3-mini class — tier-2 candidate.** Practical size for local
  CPU inference (matches this project's own resource-constrained-host
  ethos), plausible but *less certain* architectural similarity —
  genuinely needs source-level verification before commitment, more
  uncertain than Mistral. No local fixture exists today either.
- **Deliberately not chosen, with reasons (not silently omitted):**
  - **Gemma2/Gemma3** — known to use interleaved sliding-window
    attention (SWA) for alternating layers. Phase 26's own Qwen2
    vetting explicitly required `hparams.swa_type == LLAMA_SWA_TYPE_
    NONE` as a green light; SWA is exactly the kind of hybrid
    complexity the current whole-cache compression model was scoped to
    exclude. A real architectural mismatch risk, not a schedule gap.
  - **DeepSeek-family (V2/V3-class)** — uses Multi-head Latent
    Attention (MLA), a fundamentally different KV cache *shape* than
    the standard multi-head/GQA cache MEMBRANE's whole-cache
    `Q8_0`/`Q5_1` typing and `n_embd_gqa`-based byte formula assume.
    Likely incompatible with the current type-override mechanism
    entirely, not just unvalidated. Not a near-term target.

**Success bar:** at least **one** of the two (Mistral, as the primary
target) proven with real local evidence, matching Qwen2's own Phase 26
rigor exactly, before v0.4 can claim model-family expansion succeeded.
The second (Phi) is a stretch goal, explicitly allowed to not land if
its own source-level check reveals a mismatch — see Phase 37's
conditional framing in §13.

## 10. Hardware validation strategy (validation, not implementation)

Current real evidence: CPU + NVIDIA Vulkan (GTX 1650) + AMD Vulkan
RADV (integrated) — all from **one** physical developer host.

v0.4 targets, cheapest-to-hardest:

1. **CPU-only distro diversity** — the cheapest expansion: running the
   existing CPU-only path on a different Linux distro/glibc version
   (even a VM or container) needs no new GPU hardware at all.
2. **A genuinely separate physical host** for at least one more real
   Vulkan run — even one additional machine turns "one host" into "at
   least two," a meaningful trust improvement.
3. **Intel Vulkan (integrated)** — a common, currently completely
   unvalidated backend class; worth pursuing if hardware becomes
   available, not currently owned per repo evidence.

Per the Phase 32 task's own instruction: this **does not need to be a
hard blocker** for v0.4, the same precedent `v0.3.0` itself already
set by shipping with disclosed, limited validation rather than waiting
indefinitely for external testers.

## 11. Upstream `llama.cpp` strategy (investigation only, no PR)

MEMBRANE carries exactly two patches against the pinned `llama.cpp`
submodule commit, both real and re-checked this phase:

- `llama.cpp-membrane-kv-type-override.patch` — 163 lines, touching 6
  files (`include/llama.h`, `src/llama-context.cpp`,
  `src/llama-kv-cache.{cpp,h}`, `src/llama-memory.h`,
  `src/llama-model.cpp`).
- `llama.cpp-membrane-kv-device-override.patch` — 158 lines, the exact
  same 6 files.

**Assessment:** small, focused, touching one coherent area of the
codebase (KV cache construction and its public API surface) rather
than scattered across the tree — a genuinely encouraging signal for
upstream feasibility. Both hooks are generic ("override KV storage
type per layer," "override KV device placement per layer"), not
MEMBRANE-specific business logic baked into `llama.cpp` itself, which
is also a positive signal for independent usefulness to other
`llama.cpp`-based projects. **Not yet assessed:** whether upstream
`llama.cpp` maintainers would actually want this surface area (a real,
disclosed unknown — unknowable without engaging them), and this
project's own `CONTRIBUTING.md`/norms for outside contribution have
not been read against these specific patches in this planning pass.

**v0.4 scope:** a small, standalone investigation phase (§13, Phase
38) — read both patches in full, check `llama.cpp`'s own contribution
norms, write a feasibility memo. **No upstream PR opens in v0.4** (the
Phase 32 task's own explicit boundary, carried forward as that future
phase's boundary too). If upstreaming is eventually pursued, it is a
v0.5-or-later maturity item — it would directly reduce Risk R6 (patch
maintenance burden) if it ever lands, but that's a bonus outcome, not
a v0.4 commitment.

## 12. Performance strategy

**SECONDARY / DEFERRED**, per Phase 24/25's own evidence: MEMBRANE-owned
planner overhead is already tiny; model load and decode are both fully
`llama.cpp`/`ggml`-backend cost with no MEMBRANE-owned hot loop inside
either measured boundary (`docs/performance-optimization.md`). v0.4
does not re-open this investigation without genuinely new evidence.

## 13. v0.4 non-goals

Explicit, to prevent scope creep (Risk R10):

- CUDA without real local validation hardware.
- A GUI.
- Live/dynamic KV migration during inference.
- A performance rewrite (no new evidence exists to justify one).
- "All model architectures" — expansion is scoped to at most 2 targets
  this cycle, each individually source-verified.
- Windows/macOS support.
- Model downloading on the user's behalf.
- A serving/API daemon.
- Distributed inference.
- A config file / persistent user preferences (§8).
- An APT repository (§8, deferred to v0.5).
- Signed/reproducible releases (§8, deferred to v0.5).
- An actual upstream `llama.cpp` pull request (§11 — investigation
  only this cycle).

## 14. v0.4 success criteria

v0.4 is not "done" merely because features merged. Concrete, checkable
criteria:

- **UX:** a one-command (or one-command-plus-optional-inspect) flow
  exists where the user does not need to know GPU layers, KV type, KV
  placement, *or* context size for the common case; no required manual
  trial-and-error context guessing remains.
- **Compatibility:** at least one additional compressed-KV model
  family proven with real local evidence (§9's success bar).
- **Distribution:** the official `.deb` remains installable, same
  Vulkan-enabled `membrane` policy, no regression.
- **Reliability:** every existing validator/test stays green throughout
  — no regression tolerated in exchange for new features.
- **Evidence:** the context-recommendation feature has real,
  deterministic validation against real local model fixtures, not
  simulated data — matching this project's own evidence culture.
- **External validation:** improves opportunistically if available,
  explicitly not a hard blocker (same precedent `v0.3.0` itself set).

## 16. Phase roadmap

The Phase 32 task's own suggested 8-phase shape is a reasonable
starting point, but this phase's own feasibility analysis (§4-§7)
already produced enough source-level design clarity that a *separate*
"design" phase would duplicate work already done here. The sequence
below folds that in — Phase 33 goes straight to a scoped, testable
first slice instead of re-deriving the design.

- **Phase 33 — Context recommendation engine (core logic only).** Add
