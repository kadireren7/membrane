# MEMBRANE background service

Mega Phase B, PR B1. `membrane service ...` manages MEMBRANE's HTTP
server (`docs/server.md`) as a systemd **user** unit on Linux, so it
starts once and keeps running in the background — normal
OpenAI-compatible apps can talk to `http://127.0.0.1:8642/v1` without
you manually running `membrane serve` in a terminal every time. As of
Mega Phase D, PR D4, the same commands manage a launchd LaunchAgent on
macOS instead — see "macOS: launchd instead of systemd" below; this
page otherwise describes the Linux/systemd path.

`membrane serve` itself is completely unchanged and still works exactly
as before for foreground/debug use — it is also literally what the
generated unit's own `ExecStart` runs.

## Quickstart

```
membrane model add qwen /path/to/model.gguf
membrane service install
membrane service start
membrane service status
```

Then point any OpenAI-compatible client at `http://127.0.0.1:8642/v1`
(see `docs/server.md`/`docs/openai-api.md`).

## Commands

| Command | Effect |
|---|---|
| `membrane service install` | Writes a systemd `--user` unit and runs `systemctl --user daemon-reload`. Does **not** start the service. |
| `membrane service uninstall` | Stops the service (best-effort) and removes the unit file. |
| `membrane service start` / `stop` / `restart` | Thin wrapper over `systemctl --user <verb> membrane.service`. |
| `membrane service status` | Combines real `systemctl --user show` state (installed/active/pid) with a real `GET /v1/status` call against the running server — never fakes loaded-model status from a config file. |
| `membrane service logs [-n N]` | Delegates to `journalctl --user -u membrane.service -n N --no-pager` (default 50, bounded to [1, 10000]). |

`install` options: `--exec-path PATH` (use `PATH` instead of resolving
this binary's own real path via `/proc/self/exe`), `--force` (overwrite
a same-named unit MEMBRANE did not create).

## Why systemd `--user`, not a custom daemon

On Linux, systemd `--user` is the standard per-user service manager on
every mainstream distribution MEMBRANE supports — a bounded restart
policy, a supervised process, real logs via `journalctl`, and clean
SIGTERM shutdown all come for free, correctly, without MEMBRANE
reimplementing a fork/double-fork supervisor of its own. (Before Mega
Phase D, this project targeted Linux only; see "macOS: launchd instead
of systemd" below for the same reasoning applied to macOS's own
per-user service manager.)

## The generated unit

Written to `$XDG_CONFIG_HOME/systemd/user/membrane.service`, falling
back to `$HOME/.config/systemd/user/membrane.service` — **never**
`/etc/systemd/system`, never root, no `sudo` anywhere in this
command's implementation.

```ini
# Generated by `membrane service install` -- managed by MEMBRANE, safe to regenerate
[Unit]
Description=MEMBRANE local inference server

[Service]
Type=simple
ExecStart="/path/to/membrane" serve
Restart=on-failure
RestartSec=2

[Install]
WantedBy=default.target
```

- `Restart=on-failure` / `RestartSec=2` — bounded restart policy, never
  an aggressive/immediate restart loop.
- `ExecStart` carries no `--port`/`--bind`/model flags — those live in
  the server config file below, so changing them never requires
  reinstalling the unit.
- No `Requires=network-online.target` — this is a loopback-only local
  service with no external network dependency.
- Ordinary user permissions throughout; no elevated capabilities.

`install` refuses to overwrite a same-named unit it did not generate
(detected by the leading marker comment line) unless `--force` is
passed — it will never blindly clobber an unrelated unit that happens
to also be named `membrane.service`.

### `--exec-path` and development builds

`install` resolves the *currently running* `membrane` binary's own
real path via `/proc/self/exe`. If that path looks like a development
build directory (contains `/build` or starts with `/tmp/`), a warning
is printed but installation still proceeds — the generated unit will
break if that build directory is later removed or rebuilt. Pass
`--exec-path` explicitly once installed system-wide (e.g. via the
`.deb` package, which puts `membrane` on `PATH`), or reinstall the
service after packaging.

## Server config

`membrane serve` (and therefore the systemd unit, which calls it with
no flags) reads `~/.config/membrane/server.json` before parsing any
CLI flags — an explicit `--port`/`--bind` always overrides it. This is
what lets the unit's own `ExecStart` stay a fixed, simple command line
forever.

```json
{
  "schema_version": 1,
  "listen_address": "127.0.0.1",
  "port": 8642,
  "default_model": "",
  "log_level": "info"
}
```

Kept deliberately minimal — this is not intended to grow into a large
configuration system. `install` seeds this file with defaults only if
it does not already exist; it never overwrites an existing config.
`default_model` is normally set via `membrane model use NAME`
(`docs/server.md`'s own "Default model" section), not hand-edited.

A missing config file is not an error (defaults apply). A config file
that exists but fails to parse, or carries a `schema_version` this
build does not understand, is reported as a warning by `membrane
serve` and does not block startup — sensible defaults are always
available. `schema_version` exists so a future incompatible config
shape can be rejected explicitly rather than silently misinterpreted;
an existing config is never silently rewritten by a package upgrade.

## Status

```
$ membrane service status
Service:
  installed: yes
  state: active (running)
  pid: 1234567
  running: yes
  endpoint: http://127.0.0.1:8642
  loaded model: qwen
  backend: CPU
  kv precision: q8
  context policy: automatic
```

`installed`/`state`/`pid` come from a real `systemctl --user show`
call; `running`/`endpoint`/`loaded model`/… come from a real `GET
/v1/status` call against the server itself (the same endpoint
`membrane status` — the pre-existing thin HTTP client, unrelated to
the service manager — already used). If the process is active but not
yet answering HTTP (e.g. still loading), `http: not reachable at
<address>:<port>` is shown instead of fabricating a loaded-model
value.

## Model registry and default-model reload

As of PR B3, the model registry **is** hot-reloaded: a model registered
or removed with `membrane model add`/`remove` while the service is
already running becomes visible on the next `GET /v1/models` or
`POST /v1/chat/completions` call, no restart needed (a cheap `stat()`
poll, real reload only on an actual mtime change — see
`docs/server.md`'s own "Model registry hot-reload" section for the full
detail and real evidence).

The server **config** (`~/.config/membrane/server.json`, including
`default_model`) is still read only once, at `membrane serve` startup —
a newly set `default_model` (`membrane model use NAME`) takes effect on
the next `membrane serve`/`membrane service restart`, not live. This
remains a disclosed limitation, not silently assumed to already work.

## Security scope

Unchanged from `docs/server.md`: loopback-only (`127.0.0.1`) by
default, no authentication, no telemetry. Running the server as a
background service does not change this — a non-default bind address
still requires the server's own `--allow-non-loopback` flag (settable
today only via `membrane serve` directly, not yet exposed as a service
config field) and prints a strong warning when used. Remote exposure
without an authentication layer, which this project does not yet
have, is unsafe and unsupported.

## Uninstalling

```
membrane service stop
membrane service uninstall
```

`uninstall` refuses to remove a unit it did not generate (same marker
check as `install`'s overwrite guard). It stops the unit (best-effort,
errors ignored — the unit may already be stopped), removes the unit
file, and runs `daemon-reload`. It does not remove
`~/.config/membrane/server.json` or the model registry — those are
your data, not service-management state.

## Startup robustness (PR B4)

`membrane serve` (and therefore the service, which just runs it) starts
in a healthy, degraded-but-valid state rather than refusing to start,
for every one of these — all confirmed directly:

| Condition | Real behavior |
|---|---|
| Registry file missing | Starts with an empty model list — not an error (Section 8 of Mega Phase A). |
| Config file missing | Starts with defaults (`127.0.0.1:8642`, no default model). |
| Config file malformed (invalid JSON) | A `WARNING` is printed to stderr; startup still proceeds with defaults. |
| `default_model` configured but not (or no longer) registered | Starts normally, healthy — the dangling name only surfaces as a normal `404 MODEL_NOT_FOUND` on a request that actually omits `"model"` and falls back to it. |
| Port already in use | **Fails to start**, a clear message to stderr, real nonzero exit code — this is the one case that IS a hard failure, by design (Section 47). A real bug was found and fixed here: cpp-httplib's own default socket options set `SO_REUSEPORT`, which used to let a second instance silently bind the same port while the first kept running; fixed to `SO_REUSEADDR` only (a legitimate quick restart, e.g. systemd's own `RestartSec=2`, still works). |
| No Vulkan / CPU-only host | Runs correctly CPU-only — this is the default for every build without `-DGGML_VULKAN=ON`, exercised by essentially every real smoke test in this project. |

## Service upgrade / config versioning (PR B4, Section 48 of the task)

A package upgrade never touches `~/.config/membrane/server.json`, the
model registry, or the generated systemd unit — all three are user
data/state living outside the package's own install tree. `membrane
service install` itself only ever writes the unit file (refusing to
overwrite one it did not generate, see "The generated unit" above) and
seeds a server config **only if none exists yet** — an existing config
from a previous version is never rewritten.

`server_config.h`'s own `schema_version` field exists precisely so a
future, genuinely incompatible config shape can be rejected explicitly
(a real, tested failure mode — see `docs/server.md`) rather than
silently misinterpreted. No schema migration exists yet because
`schema_version` has never needed to change since it was introduced —
this is a real capability, not a promise this phase invented but did
not build.

## macOS: launchd instead of systemd

Mega Phase D, PR D4. On macOS/Darwin, `membrane service ...` manages a
per-user launchd **LaunchAgent** instead of a systemd unit —
`server.h`'s own foreground `membrane_server_run()` (`membrane serve`)
is completely unchanged and identical on both platforms; only the
background-supervision mechanism differs (`service_cmd.cpp` dispatches
internally via `#ifdef __APPLE__`, `launchd_unit.h`/`systemd_unit.h`
are fully separate, pure, independently-tested generation modules).

launchd's own command set has no exact 1:1 mapping to
systemctl's start/stop/restart/status — real, disclosed differences:

| Command | Linux (systemd) | macOS (launchd) |
|---|---|---|
| `install` | Writes the unit, runs `daemon-reload` | Writes the plist only — launchd discovers its content fresh at the point it is actually loaded, no reload step exists |
| `start` | `systemctl --user start` | `launchctl bootstrap gui/<uid> <plist>`; if already loaded, falls back to `launchctl kickstart -k gui/<uid>/com.membrane.server` — together idempotent either way |
| `stop` | `systemctl --user stop` (job stays loaded, restartable) | `launchctl bootout gui/<uid>/com.membrane.server` — this fully **unloads** the job (closer to systemd's stop+disable combined); a subsequent `start` re-bootstraps it fresh, which is idempotent but not byte-for-byte the same lifecycle |
| `restart` | `systemctl --user restart` | `launchctl kickstart -k gui/<uid>/com.membrane.server` (kill and relaunch in place) — requires the job already be loaded; run `start` first otherwise |
| `status` | `systemctl --user show --property=...` (documented, stable output) | `launchctl print gui/<uid>/com.membrane.server`, parsed for `state = ` / `pid = ` lines — a real, widely-relied-upon convention, but launchctl's own output format carries no documented stability guarantee the way systemd's `--property=` selection does |
| `logs` | `journalctl --user -u membrane.service -n N` | `tail -n N` of a real log file — launchd has no journal; the plist redirects the job's own stdout/stderr straight to `$HOME/Library/Logs/membrane/membrane.log` via `StandardOutPath`/`StandardErrorPath` |

The generated plist (`$HOME/Library/LaunchAgents/com.membrane.server.plist`,
`MEMBRANE_LAUNCHD_USER_DIR` overrides the directory for tests/CI, same
override pattern as `MEMBRANE_SYSTEMD_USER_DIR`):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<!-- Generated by `membrane service install` -- managed by MEMBRANE, safe to regenerate -->
<plist version="1.0">
<dict>
	<key>Label</key>
	<string>com.membrane.server</string>
	<key>ProgramArguments</key>
	<array>
		<string>/path/to/membrane</string>
		<string>serve</string>
	</array>
	<key>RunAtLoad</key>
	<false/>
	<key>KeepAlive</key>
	<dict>
		<key>SuccessfulExit</key>
		<false/>
	</dict>
	<key>ThrottleInterval</key>
	<integer>2</integer>
	<key>StandardOutPath</key>
	<string>/path/to/membrane.log</string>
	<key>StandardErrorPath</key>
	<string>/path/to/membrane.log</string>
</dict>
</plist>
```

- `RunAtLoad=false` — nothing auto-starts at login, matching the
  Linux unit's own no-auto-start-at-boot policy (`membrane service
  start` is the one, explicit way either platform actually starts).
- `KeepAlive`/`SuccessfulExit=false` — launchd's closest analog to
  `Restart=on-failure` (restart only on a non-zero exit).
- `ThrottleInterval=2` — a bounded restart-throttle floor, launchd's
  own closest analog to `RestartSec=2`; **not identical semantics**
  (`RestartSec` is a fixed post-exit delay, `ThrottleInterval` is a
  floor on how often launchd will relaunch at all) — disclosed here
  rather than claimed equivalent.
- Ordinary per-user LaunchAgent — no root, no System LaunchDaemon
  privileges of any kind, matching the Linux unit's own no-elevated-
  capability policy.

`--exec-path`/`--force` behave identically to the Linux path.
`resolve_exec_path()` uses `_NSGetExecutablePath()` (there is no
`/proc` filesystem on Darwin) instead of `/proc/self/exe`, resolved
through `realpath()` the same way.
