# v1.0 readiness assessment

Written after `v0.4.0` shipped (Mega Phase C, Sections 66-67 of that
task). This is an honest classification, not a roadmap commitment — no
v1.0 work is started by this document.

## Classification: **NOT_READY**

`v1.0` implies a stability/maturity promise this project cannot yet
honestly make. The evidence below is what would need to change first.

## Evidence

- **Independent multi-host validation has never happened.** Every real
  backend claim (CPU, NVIDIA Vulkan, AMD Vulkan RADV) across `v0.2.0`
  through `v0.4.0` comes from the maintainer's own single development
  host — disclosed explicitly in every release's own notes
  (`docs/release-v0.2.0-rc1.md` through `docs/release-v0.4.0.md`),
  never hidden, but never resolved either. A `v1.0` claim without at
  least one genuinely independent physical environment (different
  distro, different GPU vendor/driver stack, a different person
  running it) would be premature by this project's own stated
  standard.
- **No real external user has been observed using this project.**
  Every "real" test in this repository's own history — soak tests,
  concurrency tests, client validation, container installs — is the
  maintainer exercising their own software. There is no GitHub issue,
  no external bug report, no external contribution, no evidence of
  anyone other than the maintainer having installed and run MEMBRANE.
  `v1.0` conventionally signals "other people can depend on this"; that
  signal does not exist yet.
- **The API surface is young.** `docs/api-contract.md`'s own versioning
  policy was written this same mega-phase (`v0.4.0`) — it has never
  been exercised by an actual `/v1/` breaking-change decision, and the
  frozen error contract has existed for one release cycle. A policy
  that has never been tested by a real change is a plan, not a track
  record.
- **Compressed-KV compatibility is narrow.** Two architectures
  (`llama`, `qwen2`), specific model fixtures within each, not a
  general claim (`docs/compatibility.md`) — unchanged since `v0.3.0`.
- **No CUDA, no continuous batching, no multi-model residency, no
  distributed inference** — all explicitly out of scope for this
  entire mega-phase and not evaluated for v1.0 by this document either
  (a `v1.0` decision is about maturity/stability of what already
  exists, not about adding these).
- **What v0.4.0 DID establish, and does count in v1.0's favor
  eventually:** a real, tested onboarding path (`membrane setup`/
  `doctor`), a real, reproducible, SBOM'd release/packaging pipeline, a
  frozen and doc-checked error contract, real (if narrow) soak/
  concurrency evidence, a documented privacy/security audit, and a
  real, working release process (this exact `v0.4.0` tag/release being
  evidence of that process actually working end to end). These are
  real prerequisites for v1.0, not v1.0 itself.

## What would move this to CANDIDATE

Not a commitment, a description of what real evidence would need to
exist:
- At least one independent-host validation report (a different
  physical machine, ideally a different person) confirming the
  official `.deb` installs and works as documented.
- At least one real external user/issue/contribution — any signal that
  someone outside the maintainer has used this project.
- At least one full release cycle (a `v0.4.x` patch, or `v0.5.0`) where
  the `/v1/` versioning policy and frozen error contract were actually
  exercised by a real change, proving the policy holds up in practice.

## What would move this to READY

CANDIDATE criteria met, plus a deliberate, reviewed decision (not an
automatic one) that the accumulated evidence justifies the v1.0
stability promise — this document does not attempt to predict when
that will be, and no v1.0 implementation work follows from it.
